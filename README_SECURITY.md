# Настройка безопасности после обновления

## Настройка на PythonAnywhere (обязательно перед Reload)

На PythonAnywhere эти настройки нужно задавать в WSGI-файле веб-приложения, открытом через вкладку **Web → Code → WSGI configuration file**. Это специальный файл вида `/var/www/<username>_pythonanywhere_com_wsgi.py`; редактировать `wsgi.py` внутри папки проекта для этой цели не нужно.

Вставьте следующий блок в верхнюю часть WSGI-файла — **после импортов `os` и `sys`, но до строки, которая импортирует приложение** (обычно `from app import app as application`). Не удаляйте существующий блок, который добавляет папку проекта в `sys.path`, и сохраните существующий импорт приложения.

```python
import os

# Настройки production для Flask-приложения.
os.environ["APP_ENV"] = "production"
os.environ["SECRET_KEY"] = "ВСТАВЬТЕ_СЮДА_СГЕНЕРИРОВАННЫЙ_СЕКРЕТ"
os.environ["TRUSTED_HOSTS"] = "ВАШ_ЛОГИН.pythonanywhere.com"

# Только для первого успешного запуска после обновления:
# установите новый пароль администратора (не менее 12 символов).
os.environ["ADMIN_PASSWORD"] = "ВСТАВЬТЕ_НОВЫЙ_СЛОЖНЫЙ_ПАРОЛЬ"
os.environ["ADMIN_USERNAME"] = "admin"
```

Секрет сгенерируйте в Bash-консоли PythonAnywhere:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Скопируйте результат в `SECRET_KEY`. Это постоянный ключ: не генерируйте новый при каждом запуске и не публикуйте его. `TRUSTED_HOSTS` — точное имя хоста без `https://`, пути и завершающего `/`. Если сайт доступен и по адресу `username.pythonanywhere.com`, и по собственному домену, укажите оба через запятую, например `username.pythonanywhere.com,example.com,www.example.com`.

После сохранения WSGI-файла нажмите **Reload** на вкладке Web. Дождитесь успешного запуска и проверьте вход администратора. Если в старой базе был известный аккаунт `admin/admin`, при первом старте приложение заменит этот пароль на `ADMIN_PASSWORD` и отзовёт старые сессии. Если администратора в базе ещё нет, приложение создаст его с указанным именем и паролем. После успешной инициализации удалите из WSGI-файла только строки `ADMIN_PASSWORD` и `ADMIN_USERNAME`, затем снова нажмите **Reload**. `SECRET_KEY`, `APP_ENV` и `TRUSTED_HOSTS` должны остаться.

Не добавляйте WSGI-файл, секреты или пароль в Git и не присылайте их в чат. WSGI-конфигурация PythonAnywhere применяется к worker-процессам веб-приложения. Если запускаете тесты из Bash-консоли, задайте необходимые переменные отдельно в этой консоли: значения, установленные в WSGI-файле, автоматически не становятся переменными вашей интерактивной Bash-сессии.

## Перед первым запуском (общие требования)

- `APP_ENV=production`.
- `SECRET_KEY` — постоянный случайный секрет не короче 64 байт; используйте `secrets.token_hex(32)`.
- `TRUSTED_HOSTS` — точное имя хоста сайта; несколько доменов разделяются запятыми.
- `ADMIN_PASSWORD` — новый уникальный пароль администратора длиной от 12 символов; он нужен только до первой успешной инициализации или для замены старого `admin/admin`.

Без `ADMIN_PASSWORD` приложение остановит старт, если обнаружит известный старый пароль `admin` или если в базе вообще нет администратора. После успешного первого запуска переменную следует удалить из WSGI-конфигурации.

## Изменения защиты

- Подписанная Flask-cookie дополнительно привязана к серверной записи в `user_sessions`; logout отзывает её, а смена пароля или роли отзывает все сессии пользователя. Перед созданием новой сессии после входа пароль проверяется повторно под блокировкой БД — смена пароля параллельно не может «воскресить» старую авторизацию. Игровые POST также повторно проверяют сессию внутри транзакции. Срок обычной сессии — 7 дней, администраторской — 8 часов.
- В production используется cookie с префиксом `__Host-`, флагами `Secure`, `HttpOnly`, `SameSite=Lax`, без `Domain` и с `Path=/`.
- Проверяются CSRF-токен, `Origin`/`Referer` и `Sec-Fetch-Site` для небезопасных запросов.
- Вход ограничен по числу попыток на IP/логин и на IP в целом; проверки лимитов сериализованы SQLite-транзакцией, чтобы параллельные запросы не обходили ограничение. В БД хранятся HMAC-отпечатки, а не исходные IP и имена.
- После миграции имена пользователей сравниваются после Unicode NFKC-нормализации и casefold, что закрывает дубли с совместимыми Unicode-символами; при обнаружении прежних конфликтующих имён миграция останавливается с указанием ID.
- Регистрация ограничена пятью попытками с одного IP за час; лимит регистрации тоже проверяется атомарно. Попытки входа учитываются независимо от результата аутентификации.
- Установлены CSP, HSTS (только при защищённых cookie), запрет встраивания во фреймы, `nosniff`, строгая политика Referrer и `Cache-Control: no-store`. Внешний JavaScript запрещён на всех маршрутах; единственное внешнее исключение — фиксированный Chart.js на странице статистики. Его хеш присутствует и в `integrity`, и в CSP `script-src`, поэтому одного совпадения домена CDN недостаточно для выполнения скрипта. Неиспользуемые сторонние Hammer.js и zoom-плагин удалены.
- SQLite-файл создаётся с правами `0600`; проверяются обычный тип файла, владелец процесса, символические ссылки и права каталога (запись для посторонней группы и всех пользователей запрещена, кроме безопасного sticky-каталога). Соединения работают в defensive-режиме SQLite с отключённой доверенной схемой. Это ограничивает чтение БД другими локальными пользователями и снижает риск подмены файла базы.
- URL возврата после входа и переключения темы проверяются после многократного percent-декодирования; это закрывает варианты обхода проверки через `%2f`/`%5c`.
- Административные команды не принимают управляющие символы, не запускают shell и не исполняют SQL, переданный пользователем.
- Объект пользователя в запросе содержит только необходимые публичные поля; `password_hash` и `username_key` не загружаются в контекст шаблонов. Административные списки также не выбирают хеши паролей.
- Уязвимые/устаревшие pinned-зависимости заменены на Flask 3.1.3 и Werkzeug 3.1.9.

## Проверка

После установки зависимостей запустите:

```bash
pip install -r requirements.txt
python -m unittest discover -s tests -v
python -m compileall -q .
```

Интеграционные тесты проверяют подделанную cookie, повторное использование украденной cookie после logout, CSRF и cross-origin запросы, отказ в доступе обычному пользователю, open redirect, перебор паролей, дубли имён с разным регистром, заголовки безопасности и отзыв сессий после смены пароля.

## Ограничения проверки в текущей среде

Для этого проекта интеграционные тесты требуют Flask и Werkzeug из `requirements.txt`. Если они недоступны в среде проверки, как только зависимости установлены в виртуальном окружении проекта, запускайте приведённые команды там. Тесты не используют внешнюю базу и создают временную SQLite-базу.
